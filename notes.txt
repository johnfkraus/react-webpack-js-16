Now I want to update this application to React version 18. How?
Upgrading from React 16 to 18 in this setup involves three changes: dependencies, the render API, and (optionally) the JSX transform. Here's exactly what to change.

1. Update dependencies
bash
npm install react@^18 react-dom@^18
2. Update src/index.js — new root API
React 18 replaces ReactDOM.render with createRoot. This is the main breaking change.

Before (React 16):

jsx
import React from 'react';
import ReactDOM from 'react-dom';
import App from './App';

ReactDOM.render(<App />, document.getElementById('root'));
After (React 18):

jsx
import React from 'react';
import { createRoot } from 'react-dom/client';
import App from './App';

const root = createRoot(document.getElementById('root'));
root.render(<App />);
Note the import path changes from react-dom to react-dom/client.

3. babel.config.js — no changes needed
Your current config already works:

js
module.exports = {
  presets: [
    '@babel/preset-env',
    ['@babel/preset-react', { runtime: 'automatic' }],
  ],
};
Since you already have runtime: 'automatic', you can now actually drop the explicit import React from 'react' from App.js and index.js if you want — React 18 fully supports the automatic JSX runtime, so it's no longer just "safer to leave it in" as it was with 16. Not required, just cleaner:

jsx
// App.js — React import no longer needed
function App() {
  return (
    <div style={{ fontFamily: 'sans-serif', padding: '2rem' }}>
      <h1>Hello, React 18!</h1>
      <p>This app is bundled with Webpack 5 and Babel.</p>
    </div>
  );
}

export default App;
4. webpack.config.js and package.json scripts — no changes needed
Webpack, babel-loader, and html-webpack-plugin are all React-version-agnostic; nothing there needs to change.

5. Reinstall and test
bash
rm -rf node_modules package-lock.json
npm install
npm start
The clean reinstall avoids any stale React 16 artifacts lingering in node_modules causing version-mismatch warnings between react and react-dom.

What's different behaviorally
React 18 batches state updates more aggressively by default (including inside promises/timeouts, not just event handlers) — if you had any code relying on synchronous re-renders after setState-equivalent calls outside event handlers, double check it still behaves as expected.

Console will warn loudly if you forget step 2 and still call ReactDOM.render — React 18 supports it for backward compatibility but logs a deprecation warning recommending createRoot.

If you plan to add StrictMode later, React 18's StrictMode double-invokes certain lifecycle/effect functions in development to help catch bugs — expect to see effects fire twice in dev mode, that's expected and only happens in development builds.

That's the complete migration for this project. No changes needed to webpack config, Babel config, or the HTML template.

Now I want to update this application to React version 17. How?
Going from 18 back down to 17 reverses the render API change and is otherwise a no-op for the rest of your setup.

1. Update dependencies
bash
npm install react@^17 react-dom@^17
2. Revert src/index.js — back to ReactDOM.render
React 17 does not have createRoot / react-dom/client — that's an 18-only API. Revert to the legacy render call:

jsx
import React from 'react';
import ReactDOM from 'react-dom';
import App from './App';

ReactDOM.render(<App />, document.getElementById('root'));
Note the import goes back to react-dom (not react-dom/client).

3. babel.config.js — no changes needed
React 17 introduced the new JSX transform (the one runtime: 'automatic' uses), so your existing config still works as-is:

js
module.exports = {
  presets: [
    '@babel/preset-env',
    ['@babel/preset-react', { runtime: 'automatic' }],
  ],
};
Since the automatic runtime works in 17, you still don't need import React from 'react' just for JSX — same as in 18.

4. webpack.config.js and package.json scripts — no changes needed
Still React-version-agnostic.

5. Reinstall clean
bash
rm -rf node_modules package-lock.json
npm install
npm start
This matters more going downgrade than upgrade — leftover React 18 packages (react-dom/client internals, scheduler version mismatches) can cause subtle runtime errors if not fully cleared.

Behavioral differences to expect going 18 → 17
No automatic batching outside event handlers — state updates inside promises, timeouts, or native event handlers will each trigger a separate re-render again, unlike React 18's default behavior.

No concurrent features (useTransition, useDeferredValue, Suspense for data fetching) — these are 18+ only, so remove any such usage if you added it while on 18.

If you added <StrictMode>, it still works in 17, just without the double-invoke-on-effects behavior introduced in 18's StrictMode.

That's the full downgrade. Only index.js and the two React packages change.

What actually changes going 16 → 17
This is a notably light upgrade compared to 16 → 18:

New JSX transform available (via runtime: 'automatic', which you already have configured) — removes the need for React to be in scope just for JSX.

Event delegation changes: React 17 attaches event listeners to the root DOM container instead of document, which matters if you have code manually listening on document for React-related events or mixing multiple React versions on one page.

No more event pooling for SyntheticEvent — if you had any code accessing event properties asynchronously (e.g., inside a setTimeout), that pattern now works without needing event.persist().

Minor lifecycle warning cleanups, no major API removals.

That's the complete upgrade — literally just the two package versions. No render API changes, no config changes.

Things to check that could bite you in this specific app
React 19 removed some things that were only deprecated in 18. For this minimal app it's unlikely to matter, but worth a scan of App.js and any code you've added since:

React.createFactory — removed. Unlikely used here.

Old string refs (ref="myRef") — removed. Use useRef / callback refs instead.

propTypes and defaultProps on function components — no longer supported; if you added either, migrate to default parameter values and TypeScript/runtime validation elsewhere.

Legacy Context API (contextTypes, getChildContext) — removed; use createContext/useContext if you had any of this.

react-test-renderer — deprecated (not removed yet), if you add tests later prefer React Testing Library.

What's new/relevant if you want to use it later
use() hook for reading promises/context conditionally during render.

Actions and useActionState for form handling with pending/error states built in.

ref can now be passed as a plain prop to function components in some cases without forwardRef (still check current docs — this was in flux during 19's rollout).

Improved hydration error diffs, better <title>/<meta> handling if rendered directly in components.

None of these are required for your app to run — they're additive. For this project specifically, the upgrade is just the two package versions; nothing else changes.

Can I switch to vite now?
Yes — for a simple React app like this, Vite is a solid move: faster dev server, near-instant HMR, less config. Here's the full migration from your current webpack setup to Vite.

1. Remove webpack-related packages, add Vite
bash
npm uninstall webpack webpack-cli webpack-dev-server html-webpack-plugin babel-loader @babel/core @babel/preset-env @babel/preset-react
npm install --save-dev vite @vitejs/plugin-react
Note: @vitejs/plugin-react uses Babel internally under the hood but only for what it needs (JSX transform + Fast Refresh) — you don't manage Babel config yourself anymore, so babel.config.js becomes unnecessary and the whole babel-loader wiring goes away.

2. Delete these files
bash
rm webpack.config.js babel.config.js
3. Add vite.config.js at the project root
js
import { defineConfig } from 'vite';
import react from '@vitejs/plugin-react';

export default defineConfig({
  plugins: [react()],
  server: {
    port: 3000,
    open: true,
  },
});
4. Move and update public/index.html
Vite expects index.html at the project root (not inside public/), and it needs a <script type="module"> tag pointing directly at your entry file — Vite handles bundling from there, no separate plugin needed.

bash
mv public/index.html ./index.html
Then edit it to add the script tag:

xml
<!DOCTYPE html>
<html lang="en">
  <head>
    <meta charset="UTF-8" />
    <title>React 19 Vite App</title>
  </head>
  <body>
    <div id="root"></div>
    <script type="module" src="/src/index.jsx"></script>
  </body>
</html>
5. Rename your entry files to .jsx
Vite's default behavior treats .js files as plain JavaScript (not JSX) unless configured otherwise. The cleanest fix is renaming files that contain JSX:

bash
mv src/index.js src/index.jsx
mv src/App.js src/App.jsx
Contents stay the same — no code changes needed inside them:

jsx
// src/index.jsx
import React from 'react';
import { createRoot } from 'react-dom/client';
import App from './App';

const root = createRoot(document.getElementById('root'));
root.render(<App />);
jsx
// src/App.jsx
function App() {
  return (
    <div style={{ fontFamily: 'sans-serif', padding: '2rem' }}>
      <h1>Hello, React 19!</h1>
      <p>This app is bundled with Vite.</p>
    </div>
  );
}

export default App;
Note the import in App.jsx inside index.jsx stays as from './App' — Vite resolves the extension automatically, no need to write ./App.jsx.

6. Update package.json scripts
json
{
  "scripts": {
    "start": "vite",
    "build": "vite build",
    "preview": "vite preview"
  }
}
(npm start now launches Vite's dev server; keeping the script name start instead of dev matches your existing habit, but vite's own convention is usually dev — rename if you prefer.)

7. Clean reinstall
bash
rm -rf node_modules package-lock.json dist
npm install
npm start
What you gain / what changes
Dev server startup and HMR are near-instant — Vite uses native ES modules in dev, no bundling until build time.

Production builds use Rollup under the hood via vite build, output still goes to dist/.

No more manually wiring loaders/presets — @vitejs/plugin-react handles JSX + Fast Refresh out of the box.

If you later add environment variables, Vite uses import.meta.env and requires the VITE_ prefix (e.g. VITE_API_URL), unlike webpack's process.env + dotenv pattern.

That's the complete migration. Your React 19 code itself needs zero changes — only the build tooling and file extensions.
